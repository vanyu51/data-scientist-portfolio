# Batch-признаки клиентов в Airflow: пайплайн Postgres → признаки → S3

Пайплайн, который регулярно готовит витрину признаков для ML-моделей интернет-магазина: читает данные из PostgreSQL, считает поведенческие и денежные признаки по каждому клиенту на заданную дату и складывает результат в S3.

## Что делает пайплайн

1. Читает четыре таблицы: `customers`, `sessions`, `events`, `orders`
2. Предобрабатывает данные: приводит типы, удаляет дубликаты по `event_id` и `order_id`, нечисловые суммы заказов заменяет на 0
3. Считает признаки на дату среза `run_date` (окна 7 и 30 дней)
4. Сохраняет CSV и загружает в S3 по пути `run_date=<дата>/batch_features.csv`
5. Отдельной задачей проверяет, что файл в S3 существует и не пустой

## Признаки (одна строка = клиент + `run_date`)

| Группа | Признаки |
|---|---|
| Активность (7д, 30д) | просмотры, добавления в корзину, число сессий, уникальные товары |
| Конверсии (7д, 30д) | просмотр → корзина, корзина → покупка |
| Сессии (30д) | средняя длина сессии |
| Деньги (30д) | число заказов, сумма и средний чек |
| Давность | дней с последнего заказа (`-1`, если заказов нет) |

## Что делал

- Защитился от утечки из будущего: до любых агрегаций оставляю только события с `timestamp < run_date`, сессии и заказы аналогично, а в каркас берутся только клиенты, зарегистрированные до среза
- Событиям, где нет `customer_id`, присоединяю его через сессии, уже отфильтрованные по дате
- Продумал граничные случаи: деление на ноль в конверсиях, клиент без заказов, сессия без событий, строки без `product_id`
- Разделил код на два слоя: расчёт признаков (`calculate_batch_features.py`) и оркестрация (`batch_features.py`)
- Настроил подключения через **Airflow Connections** (Postgres, S3) и параметр среза через **Airflow Variable**, секреты в код не попадают
- Результат каждого запуска пишется в отдельную папку `run_date=...`, поэтому повторный запуск на ту же дату перезаписывает файл и не создаёт дубликатов
- Добавил задачу валидации результата в S3 (`head_object`, проверка размера)

## Структура

```
dags/
├── batch_features.py             # DAG: расчёт и загрузка, затем проверка
└── calculate_batch_features.py   # чтение данных, признаки, сохранение
```

## Настройка

| Что | Ключ | Пример |
|---|---|---|
| Variable | `batch_features_run_date` | `2025-09-01` |
| Connection (Postgres) | `ecommerce_db` | чтение исходных таблиц |
| Connection (S3) | `aws_default` | в Extra: `bucket`, `endpoint_url`, ключи доступа |

Ключи и пароли хранятся только в Airflow, в репозитории их нет.

## Что можно улучшить

- Сейчас DAG запускается вручную (`schedule=None`), дата среза берётся из Variable; для регулярных запусков стоит брать дату из контекста запуска Airflow
- Читаются таблицы целиком; на больших данных расчёт стоит вынести в SQL или читать только нужное окно
- Нет автоматических тестов на расчёт признаков (например, на малом наборе с известным ответом)

## Стек

Python, `pandas`, `numpy`, `SQLAlchemy`, Apache Airflow (TaskFlow API, `PostgresHook`), `boto3`, PostgreSQL, S3 (Yandex Object Storage)
